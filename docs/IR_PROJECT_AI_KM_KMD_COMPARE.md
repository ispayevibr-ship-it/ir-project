# IR Project AI — сопоставление КМ и КМД

**Состояние:** новый этап в отдельной ветке `feature/ir-project-ai-next`. Рабочая версия IR Project 1.7.217 остаётся без изменений. По просьбе пользователя промежуточные тесты, скачивание нейросетей, сборку и релиз не запускаем; полная приёмка — после завершения всех этапов.

## 1. Назначение

Подготовить доказуемый журнал проверок **КМ ↔ КМД** по реальным загруженным PDF. Каждый параметр привязывается **к двум независимым первоисточникам** с раздельными SHA-256, листами, позициями и ревизиями. Отдельное совпадение **не означает**, что все чертежи и расчёты проекта проверены.

На данном этапе инженер **сам указывает два значения** по исходным чертежам. После подключения Qwen/PaddleOCR локальная модель сможет создавать предложения с пометкой «Требует проверки», но не подтверждать их автоматически. Доступ к исходным файлам не заменяется ответом нейросети.

## 2. Контролируемые показатели

Для каждой пары «марка/участок + шифр + позиция/узел + проверяемый параметр» предусмотрены:

- **Количество экземпляров отправочной марки, шт.**
- Профиль и сечение, марка стали.
- Длина, ширина, толщина, отметка (мм).
- Масса (кг).
- Количество метизов, число физических соединений, длина шва.
- Тип/обозначение соединения.
- Обозначение изменения/ревизии.
- Другой текстовый параметр с явным описанием.

Текстовое сравнение допускает различия регистра и двойных пробелов, но **не объединяет латинскую K и кириллическую К** и не переименовывает профили по предположению. Числа сравниваются по значениям, `КМД − КМ` показывается как разность. Допуск по умолчанию **0**; любой положительный числовой допуск явно вводит инженер и обосновывает комментарием. Для количеств допуск не допускается.

## 3. Первичные источники

Слева: загруженный PDF **КМ**, справа: загруженный PDF **КМД**. Для обоих обязательны:
- ID документа внутри текущего объекта;
- совпадающая с оригинальной записью SHA-256;
- номер листа, позиция/место на листе;
- указанная инженером ревизия/изменение.

Запись с изменённым или отсутствующим источником получает результат **«Источник изменён/удалён»**, не засчитывается в проверенные показатели и остаётся в истории. Наличие нового PDF в объекте **само по себе не означает**, что старый автоматически устарел: выбор действующей ревизии требует отдельного механизма управления комплектами/ревизиями (следующий этап).

## 4. Результат и решение инженера

Программа показывает вычисленный результат:
- **Соответствует** — оба введённых значения совпали с учётом указанного явного допуска.
- **Расхождение** — значения отличаются.
- **Источник изменён/удалён** — нарушена цепочка источника.
- **Не хватает данных** — запись не может быть сопоставлена.

Инженер отдельно выбирает статус: **Требует проверки / Проверено инженером / Отклонено**.

Для подтверждённого совпадения нужно решение **«Соответствует»**. Для подтверждённого расхождения — **«Необходимо исправление»** или **«Принятое отклонение»** (в последнем случае с обязательным обоснованием). Принятое отклонение **остаётся расхождением**, не переписывает ни один исходный PDF и не создаёт новую исправленную версию КМД.

Сводка показывает отдельно: соответствия, замечания, требующие исправления, принятые отклонения, записи без решения, недействительные источники и отклонённые записи. Итог **всегда частичный**, пока весь комплект не прошёл сквозную приёмку.

## 5. Доступ и история

- Просмотр доступен в рамках текущего доступа пользователя к объекту в существующем Electron-приложении.
- Редактирование требует прав администратора/инженера и повторной проверки их пароля через IPC.
- Каждая запись проверяется по `expectedRevision`: нельзя незаметно перезаписать исправление из другого окна.
- Решение и история сохраняются одной транзакцией SQLite.
- Данные изолированы в `object_records.section_key="ai-km-kmd-comparison"`; история — `ai-km-kmd-comparison-history`.
- Один активный параметр одной марки/шифра/позиции не может учитываться повторно. Для нескольких соединений нужно явно различать коды позиций.
- Основные ведомости, готовность объекта, монтажная схема, 3D и ежедневные отчёты **не изменяются**.

## 6. Пользовательский сценарий

1. Добавить PDF КМ и КМД в тот же объект, указав тип каждого документа.
2. Открыть **ИИ-распознавание → Сравнение КМ / КМД → Добавить сравнение**.
3. Выбрать марку/позицию/тип параметра.
4. Выбрать лист и указать фактическое значение КМ.
5. Выбрать лист и указать фактическое значение КМД.
6. Просмотреть предварительное соответствие/разницу.
7. Подтвердить инженерным паролем решение или оставить его на проверке.
8. В перечне открыть два первоисточника, перейти к истории, отфильтровать расхождения.

## 7. Изменённые файлы

- `src/ai-km-kmd-compare.js` — сравнение, раздельные источники, валидация, вычисление разницы, решения и журнал.
- `src/ai-compare-page.js` / `src/ai-compare-page.css` — экран сравнения, формы, фильтры и источники.
- `src/ai-recognition-page.js`, `src/index.html` — подключение вкладки.
- `main.js`, `preload.js` — IPC чтения и записи с существующей сессией проверки.
- `scripts/test-ai-km-kmd-compare.js` — **подготовленный, но не запущенный** контрактный тест.

## 8. Что не сделано в этом этапе

- Сравнение **пока не автоматическое**: распознавание значений из листов требует реально установленной локальной нейросети и отдельного механизма подтверждения.
- Не реализована проверка всех геометрических зависимостей, узлов и расчётов КМ и КМД на уровне САПР/BIM.
- Не создан контроль актуальной редакции **целого комплекта** листов: при одновременном хранении исходного и изменённого PDF оба могут иметь корректные SHA.
- Не реализовано распределение сессионных ролей по объектам с серверной авторизацией; это отдельный завершающий этап основной программы.
- Нет автоматической публикации списка расхождений в производственную часть проекта.
- Не проверялись тесты, логика DOM, SQLite, Windows-сборка и настоящая модель: всё оставлено на финальный этап по указанию пользователя.
